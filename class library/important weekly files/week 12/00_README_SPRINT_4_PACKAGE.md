# Sprint 4 Package: QA + Refactor + Professional Polish

Sprint 4 covers **Weeks 12–14**.

The goal is not to add more features. The goal is to make the project reliable enough for final demo, technical defense, and handoff.

## Sprint 4 Theme

**QA + Refactor + Professional Polish**

Teams should prove that their app:

- runs,
- has a stable core flow,
- has visible bugs,
- has assigned owners,
- has tested fixes,
- has cleaner code,
- has useful setup/docs,
- has a reliable demo/deploy plan,
- and has linked evidence in GitHub.

## Weekly Focus

| Week | Focus | Main output |
|---:|---|---|
| Week 12 | QA Day | QA checklist + bug severity list |
| Week 13 | Refactor + Documentation | cleanup PRs + setup/architecture docs |
| Week 14 | Deployment + Polish | stable demo/deploy plan + final polish checklist |

## Folder Guide

- `01_Sprint_4_Overview/` — student and instructor overview materials.
- `02_Week_12_QA_Day/` — QA checklist, bug severity, bug reports, class plan, deck plan.
- `03_Week_13_Refactor_Docs/` — refactor rules, documentation templates, class plan.
- `04_Week_14_Deployment_Polish/` — deployment/demo readiness and polish materials.
- `05_Sprint_Packet_and_Grading/` — Sprint Packet add-ons, receipts guide, grading scan.
- `06_Common_Templates/` — reusable PR, Copilot, and AI workflow templates.
- `07_Source_Reference_Files/` — copied course source files already used in this unit.

## Non-Negotiables

1. GitHub is the source of truth.
2. If it is not linked, it did not happen.
3. One Weekly Sprint Packet per team per week.
4. Every student posts 2–3 linked Contribution Receipts.
5. Every class includes a Weekly Progress Demo.
6. AI-assisted work only counts if the team can run it, explain it, test it, debug it, and link evidence.
7. No new features unless the core flow is stable and understood.
