# Sprint 4 Guide: QA + Refactor + Professional Polish

## Purpose

Sprint 4 is about making your MVP reliable.

You are not trying to impress people with more features. You are proving that your app is real, stable, explainable, and ready for final demo.

## Sprint 4 Weeks

| Week | Focus | What you submit Friday |
|---:|---|---|
| Week 12 | QA Day | Weekly Sprint Packet + QA checklist + bug severity list |
| Week 13 | Refactor + Documentation | Weekly Sprint Packet + cleanup PRs + docs updates |
| Week 14 | Deployment + Polish | Weekly Sprint Packet + stable demo/deploy plan |

## Sprint 4 Rules

- Test the core flow before adding new features.
- Turn bugs into GitHub Issues.
- Assign every bug an owner.
- Use severity labels: P0, P1, P2, P3.
- Keep PRs small and connected to Issues.
- Update `/docs` so another person can understand and run the app.
- Show evidence every week.
- Keep AI use transparent.

## Definition of Done for Sprint 4

By the end of Sprint 4, your team should be able to show:

- [ ] The app runs locally or has a reliable deployed demo.
- [ ] The main MVP flow works.
- [ ] P0 bugs are fixed or clearly documented with a backup plan.
- [ ] P1 bugs are fixed, assigned, or explained with a realistic workaround.
- [ ] QA checklist is updated.
- [ ] Setup instructions are accurate.
- [ ] Architecture/docs explain the main parts of the app.
- [ ] Every member can explain one meaningful contribution.
- [ ] AI-assisted work is reviewed, tested, and documented.

## What Good Looks Like

```md
This week we tested our main MVP flow from signup to item creation.
We found one P1 bug and three P2 bugs.
We created Issues for each bug, assigned owners, and linked screenshots.
We fixed the P1 bug in PR #24 and tested it manually.
Our setup guide was updated because one teammate could not run the app at first.
```

## Weak Work

- “We fixed bugs.”
- “It works.”
- “Almost done.”
- “AI helped.”
- “The code is on someone’s laptop.”
- “We added new features but did not test the old ones.”

That is not enough.

## Sprint 4 Reminder

A visible bug is useful. A hidden bug is dangerous. A vague bug is useless.
